# 测试与验证

## 本地入口

在仓库根目录使用 Python 3.10+，无第三方 Python 依赖：

```sh
python3 scripts/check_harness.py
python3 -m unittest discover -s tests -v
git diff --check
```

检查器覆盖六个固定入口、Skill 元数据、Notes 分类/命名/格式/状态与归档冻结，以及支持范围内的本地 Markdown 文件链接。它不执行文档命令，不验证业务行为、文档语义、外部链接、锚点或参考式链接。冻结归档的出链是历史事实，不按当前文件存在性验证。

单元测试在隔离目录构造正反例，不证明 Agent 必然发现或遵守 Skill，也不替代派生项目的业务测试。已有上游命令不能直接当成本模板的检查结果。

## 归档验证

归档规范与操作见 [Notes 规范](../.agents/notes/README.md) 和 [归档 Skill](../.agents/skills/seed-notes/SKILL.md)。普通检查只读，封存是显式写操作。新归档进入封存前先核对生命周期及内容；封存工具不能把旧归档的改动合法化。

本地默认对比 Git `HEAD`，可用 `HARNESS_ARCHIVE_BASE_REF` 指定可信的变更前提交。CI 使用完整 Git 历史：PR 对比事件的 base SHA，push 对比事件的 before SHA；首次推送的全零 SHA 表示没有旧基准。正文与封存清单同时修改，也不能覆盖可信基准里的旧记录。基准缺失或不可读时不能把非空归档报告为验证通过。

本地 `HEAD` 只能检查相对该提交的变化，已经提交的更改需要选择更早的可信基准。CI 配置不是防篡改安全系统：若连工作流或检查代码都被修改，仍需要代码审查与平台权限控制；本模板不自动配置分支保护。

## CI 与业务项目

GitHub Actions 执行相同检查器和单元测试，并检查当前提交全部跟踪文件的空白错误。是否通过必须以精确提交的远端结果为准，本地测试不能代替远端运行。

派生项目初始化时建立真实业务验证并接入本地与 CI。业务函数、接口、数据库、构建产物、UI 各按实际行为验证；保留模板检查不意味着业务已验证。初始化交接见 [seed-initialize](../.agents/skills/seed-initialize/SKILL.md)。

## 实际 Agent 场景验收

在独立临时目录使用模板，给新上下文任务目标，不提示应该读取哪一个 Skill；按产物和行为判断，不能把关键词命中当成成功。

- 初始化后另起上下文增加独立模块：事实文档同步、必要模块说明建立，普通任务不重新初始化。
- 只要求审查规则或文档变更：能找到合适方法并只读报告，不因缺少业务代码拒绝审查。
- 设计模型可见工具或 Skill：能发现 Agent 体验方法，不误入初始化或全仓整理。
- 普通修订与明确按名称调用翻译分开：前者不自动启动扩展翻译流程，后者遵守明确范围。
- 新建、取代与归档 Notes：按局部规则处理，正常迁移通过；错误正文、状态和旧归档修改由真实 CLI 拒绝。
- 性能、响应式、简化与升级任务：能找到对应独立入口；没有相关变化时不批量加载或新增材料。

以上是可复现的验收方法，不是已经全部通过的声明。每次交付分别报告机器检查、内容审查、实际 Agent 任务、未运行范围和证据对应版本。历史执行过程保留在提交或交付记录，不在本页持续追加。

## 验证边界

本模板没有业务服务或 UI。完整多模块演进、初始化中断恢复、真实浏览器录制、性能优化、发布/合并、双语工作流、不同宿主的自动发现和调用元数据执行，不由当前 CI 覆盖。中文预算、段落换行和完整 Markdown 语法也没有机械等价保证。上游取舍见 [迁移映射](upstream-mapping.md)。
