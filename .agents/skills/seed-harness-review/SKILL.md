# 审查工程治理

本 Skill 审查规则和知识体系，不替代代码审查。只读请求只输出发现，修复需要授权；一次异常不是增加全局永久规则的充分理由。

## 建立审查范围

确认具体症状、目标文件或差异、当前宿主及用户期望。读取真实根入口、局部规则、Skill 和受影响事实来源，不按目录数量或篇幅直接评价好坏。

## 按实际任务检查

- 入口：新会话能否找到真实项目目标、适用局部约束及验证入口？不要依赖前一会话背景。
- 路由：描述能否区分初始化、普通变更、文档维护、代码审查与治理审查？无关技能是否被全部常驻加载？宿主未自动发现时是否有明确文件入口？
- 归属：同一事实是否多处手工维护？局部例外是否不必要地提升成全局约束？文档和 Skill 是否互相复制教程？
- 生命周期：初始化是否退场，中途状态是否可恢复，临时结论是否已归位，旧规则是否已被实现或架构替代？
- 验证：模板测试是否被当成业务验收，本地命令与 CI 是否一致，报告是否区分格式、行为、跨会话和远端结果？
- 负担：每项规则是否改变真实决策？新文件是否解决已有文档不适合回答的问题？不得为精简而删安全和失败约束。

## 输出与修复

每条发现给出位置、触发场景、影响和证据；把已复现缺陷、静态风险与建议区分。明确已检查和未检查范围，不声称全面正确。

获授权时先修改最小权威来源，再更新引用和适用检查。不要从上游批量覆盖项目定制。用同一失败场景验证修正，并选择相邻场景检查退化：空项目、单文件工具、模块演进、初始化后的普通任务、只读审查或新会话接手。脚本模拟和实际 Agent 执行分开报告。
