# 实施项目变更

本参考连接需求、实现和交付，不代替项目架构、业务规则或专项验证。先读取适用 AGENTS、模块 README 和实际配置，不能凭上次会话记忆判断当前状态。

## 建立范围

1. 确认目标仓库、分支、用户已有修改及已授权结果。不要覆盖无关工作；设计讨论不自动授权实现。
2. 将目标转成可观察的验收条件，区分已确认要求、方案选择和未知事实。现有实现不是改变业务约束的授权，新写的测试也不是需求本身。
3. 找到受影响的事实来源和接口消费者。简单修复可直接实施；跨模块、兼容性或数据迁移变化先说明边界、替代方案和恢复方式，重大未决取舍先确认。
4. 使用 [验证与交付](../../seed-verify/SKILL.md) 建立真实差异范围和证据计划。仅加载本次风险需要的参考，不默认执行全仓所有检查。

## 实施与风险分流

- 复用已有扩展点，能力及其规则尽量由实际所有者维护。新增公共接口、配置、状态机或抽象前，确认现有消费者需要；移动一个不必要的概念并不等于简化。
- 缺陷尽可能先建立失败复现，再修复；核对接口两端、真实入口与最终可见状态，不能仅让测试顺从实现。
- 失败、重试、后台任务或部分提交涉及 [错误与恢复](../../seed-error-handling/SKILL.md)。先判断结果是否已发生，再决定能否重试。
- 资源、并发、时钟、进程或平台敏感测试使用 [测试可靠性](../../seed-test-reliability/SKILL.md)。
- 有长期知识变化时使用 [文档维护](../../seed-doc/SKILL.md)；修改注释、提示词或可见文字时使用 [表达标准](../../seed-prose/SKILL.md)。只更新相关事实，不生成任务流水。

## 保持可接手

任务暂停或超出一次会话时，把继续工作必需的已确认选择、待定事项、当前状态、下一步和未验证范围留在仓库可发现的位置或项目已有任务系统，并给出入口。不要依赖聊天历史，也不要为每次小修复建立永久日志；完成后将稳定结论归入事实所有者，清理临时计划。

## 交付

按 [验证与交付](../../seed-verify/SKILL.md) 检查最终差异；高风险或用户要求的代码审查使用 [代码审查](../../seed-code-review/SKILL.md)，不能用治理审查替代。报告实际检查、范围及未完成事项。相关检查失败先修复或明确阻塞，不擅自发布；推送与发布分别依用户授权执行。
