# 精炼工程表达

## 范围与权限

从当前任务确定具体文件、模块或差异范围；无法确定时先问最小问题。审阅只报告，修改按授权执行。生成文本先修改源头，不改产物；历史决策不能改写成从未发生。

## 保留完整含义

编辑前识别执行者、动作、条件、时序、必须/允许/禁止、例外、责任、副作用、失败及后果。只有这些必要信息仍然成立，缩短才有价值。

- 公共接口：必要时说明返回差别、异常、取消、资源责任和时序。
- 模块注释：解释非显然约束、竞态或设计原因，不逐行复述代码。
- 测试说明：解释不直观的样本与断言原因，不描述显然步骤。
- 操作指南：前提、操作、可观察结果与重要失败恢复。
- README：读者实际需要的用途、契约、限制和入口，不堆内部整理计划。
- Skill：改变 Agent 决策的规则和标准，不重复通用能力说明。

## 编辑判断

对每处选择保留、补充、精简、恢复、重组或暂缓。术语保持一致，优先具体对象与动词；中文正文自然表达，命令、文件名和 API 标识保留准确形式。

详细解释尽量有唯一归属，但直接影响安全使用的短约束可以就地保留。字数不是完成指标，不为阈值拆出大量小文件。发现取舍不明确时保留事实并报告，不擅自简化契约。

## 例子

- 不好：“停止时清理资源。”更完整：“先请求取消，等待工作线程退出后再释放资源。”后者保留必要顺序，不能为了短而删掉。
- 不好：“这里判断参数是否为空，然后返回错误。”若代码显然表达此逻辑，删除该注释；若空值有业务含义，解释其原因。
- 不好：在 README 追加“今天修复了连接重试”。应修改重试行为的原说明，任务历史留在提交记录。

结束时核对语义没有被削弱，报告刻意保留和未处理的歧义。链接与结构检查使用项目已有工具；它们不能替代内容判断。
